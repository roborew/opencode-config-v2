# Decisions (D1–D37)

Decided 2026-11-14 after a design review. Detail lives in `blueprint.md`. Longer rationale for the load-bearing ones is in `../adr/`.

| D19 | **Essential roles only.** Use addy's roles where they exist, and add custom pieces only to integrate an external tool (OpenCode server, GitHub, Sysbox/Docker). A slice that can't converge stops as BLOCKED and goes back to `plan` as a spec gap.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| D20 | **Sandbox socket broker:** the host Docker socket moves out of the OpenCode container into a sandbox sidecar with a fixed API.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

The `oc-sandbox` plugin picks a backend automatically: sandbox sidecar reachable → Sysbox; otherwise a local Docker daemon → direct `docker compose -p <slice>`; otherwise BLOCKED. `OC_SANDBOX_BACKEND=auto                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | sysbox | docker` overrides the choice. Server-only behaviour (gitdir rewrite, delete guard, localhost rewrite) stays in opencode-server overrides and never lives in the config. |
| D22 | **Use OpenCode's built-in `plan` and `build` agents** as the two primaries, overridden in the config by the same ID (model, `system`, `permissions`, as described in [OpenCode agents docs](https://opencode.ai/docs/agents/)). No custom primary agents.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D23 | **No separate RED role.** This matches addy's own `/build`, where a single agent runs RED → GREEN → regression → build → commit. Test-first is enforced mechanically: the sandbox records that the test-only commit failed before the code commit, and the reviewer checks the tests weren't weakened.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| D24 | **Only addy personas as subagents:** `code-reviewer` (always, before the PR) and `security-auditor` (when risky paths change). `test-engineer` is not used. Following addy's rule, personas never call other personas, and commands do the orchestrating.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D25 | **All 25 addy skills have explicit permission ownership and activation rules.** `using-agent-skills` is always active for Plan and Build to discover contextual workflows. Deterministic gateways/slice overlays handle the core lifecycle; real task context plus `area:*`/`risk:*` labels select overlays. Skills run when applicable, not indiscriminately; per-agent permissions keep cross-responsibility workflows unavailable. Build also gets `constraint-driven-development` and `shipping-and-launch` without merge/deploy permission.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |        |
| D26 | **Plan and Build are the only public gateways.** The `oc-skills` prompt hook reads `session.agent` and always adds `using-agent-skills` plus `oc-plan-gateway`/`oc-build-gateway`, even without commands; slice records additionally compose base/area overlays. Commands enter the same workflows rather than forming a competing implementation. New work in `/plan` or bare Plan starts Define without requiring `/spec`; Plan owns both approval gates and all spec/PRD/issue writes. Session-routing errors reject prompt admission rather than silently losing required workflows. The global `AGENTS.md` carries the tested full 25-skill activation matrix.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |        |
| D27 | **Provider lock by policy:** `policies` deny `provider.use` except `opencode` (Zen) and `opencode-go`. Force-push and push-to-main are hard-denied by policy as well as by agent permissions.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| D28 | **The Project Template guides architecture without imposing a monorepo** (`templates/project/TEMPLATE.md`, informed by Rekalled). Every project has one repo, but it may be a framework-native single app (including Next.js or TanStack Start) or several apps. `apps/`, `packages/`, shared workspaces, per-app directories, API contracts, generated clients, layered backends, and particular build tools are choices used only where real boundaries require them. Common defaults are clear component ownership, appropriate Dockerfiles and lockfiles, and docs in `docs/`. It does **not** set how tests run. (Clarified 2026-11-16.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| D29 | **One `compose.yml` per repo, used only for testing, fully isolated.** It holds everything needed to run and test the whole system: actual apps from their own Dockerfiles, applicable throwaway services, test runners, any client generator, applicable E2E and the image smoke check. There is no second Compose or override file. It assumes nothing from the host: dummy env is committed and no host ports are published. On the server (OpenCode in Docker), each slice gets its own Sysbox container. On the Mac, `docker compose -p <slice>` runs directly. GitHub Actions runs the same file as the PR gate. **Compose is never used in production:** Actions builds and packages each app's image separately for deployment. (Q-A, 2026-11-14.) It uses the template's dev, test and full profiles. The flow only uses the Docker path (test-target images, any `_test` database and production images for smoke and full), never the host path.                                                                                                                                                                                                                                                                                        |
| D30 | **Vertical slices through the applicable stack in one PR:** for example migration (expand) → API RED/GREEN → regenerate the client (committed) → web RED/GREEN → E2E. Skip layers and generated artifacts that do not exist. One `area:<app>` label per logical component touched. Never split one behaviour into sequential tier-only PRs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| D31 | **The flow calls `docker compose` directly, not `just`.** The `justfile` is an optional shortcut. It should wrap the same `docker compose -f compose.yml --profile …` commands that `AGENTS.md` declares, and the flow never depends on it. The server box image stays Docker + Compose only, with no extra packages. When a repo has a `justfile`, a CI check makes sure `just test-docker` and the declared command match. (Q-B, 2026-11-14.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| D32 | **Browser E2E runs in Docker too, when the repo has browser flows.** Such a repo's `compose.yml` has an `e2e` service in the test profile, using the official Playwright image (version pinned to the repo's `@playwright/test`), running against the full-profile production images over the Compose network. Agents, the server sandbox and CI all use it, and `just e2e` stays the host path. (Q-C, 2026-11-14.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| D33 | **App repos hold no flow reference material.** PRD, slice and PR body templates and `labels.json` live only in the config (`skills/oc/oc-github/templates/`). `oc-github` creates issues and PRs with `--body-file`, and creates missing labels on demand (`area:<app>` from the `AGENTS.md` `apps:` keys). App repos hold only facts about themselves: code, `compose.yml`, Dockerfiles, CI, docs, applicable scoped skills and `AGENTS.md` front matter. (Decided 2026-11-14.) The old per-repo files (issue forms `prd-parent.yml`, `child-feature.yml` and `research.yml`, `pull_request_template.md` and `labels.yml`) are retired. Their useful parts (the PR deploy notes) are folded into the config's `pr.md`. The research form and the `state:*`, `category:*` and `mode:*` labels have no v2 equivalent: research goes through `/spec` with idea-refine, and agents never merge, so `mode:afk`/`mode:hitl` isn't needed. **`.github/` in an app repo keeps only GitHub's own files:** `workflows/` (`ci.yml`, `deploy.yml` and any others) and `dependabot.yml`. The repo owns them in full, with no shared or reusable workflow from the config. `repo-setup` writes a starting `ci.yml` once, and after that it belongs to the repo. |
| D34 | **The config repo holds only what OpenCode needs to run, plus config verification.** No fixture app repo or other app code. The flow knows single-app and multi-app architecture through the Project Template, skills and `AGENTS.md` front matter, not from an example repo. Verification is limited to config linting (§13) and small plugin tool tests using temporary repos created at test time. Acceptance runs happen on real app repos. (Decided 2026-11-14; ticket 03 removed.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| D35 | **Model roster reassessment (2026-11-16; ADR 0010):** `plan` moves to Kimi K3.1 Pro (Go), superseding D16's Opus choice; `explore`/`general` move to GLM 5.3 Flash; `code-reviewer` moves to MiniMax M3.1 Flash (same family as M3, next generation, half price). `security-auditor` stays on Qwen3.8 Max (D15) and `build` stays on DeepSeek V4.1 Flash — the builder is the flow's highest-volume role and its thinking is front-loaded into planning (D23). The setup is on Go Plus, so the Go monthly limits are the Plus ones.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| D36 | **Sandbox static checks (2026-11-25; ADR 0014):** each app repo declares its real lint/typecheck services under `test.checks` in the same Compose contract; `sandbox_check` runs them during the coding loop and `sandbox_gate` runs every declared static check before the dynamic steps. Static checks never create RED/GREEN evidence, and a checks-only contract is still invalid. CI repeats the same isolated checks as a final confirmation rather than the first discovery point.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D37 | **Plan project health check (2026-11-25; ADR 0015):** every new Define/spec phase begins with a quick read-only check of the app repo's `AGENTS.md`, test contract, and `test.checks` declarations. Gaps become explicit remediation items in the spec and go through the normal approval/slice flow; Plan never edits an app repo directly.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| D38 | **Matt skills are complete but manual-only (2026-11-25; ADR 0016):** vendor the stable release's entire promoted production set under `skills/matt/` — never beta, frozen or deprecated skills — unmodified with a pinned `Matt-Sync` provenance contract. One `/matts-skills` command presents the workflows and dispatches only an explicit user choice. Plan and Build receive no Matt skills, and `oc-skills` never routes them. `/sync-skills` resolves the latest stable Addy and Matt releases to full SHAs, shows one diff plus lifecycle impact, and applies only after approval; a new Addy skill is never activated implicitly. Two manual utility agents (`matt`, `skill-admin`) keep workflow execution and upstream maintenance separate from the two lifecycle gateways.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
